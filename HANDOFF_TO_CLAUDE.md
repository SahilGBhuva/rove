# Rove handoff to Claude Cowork

Updated: October 17, 2026. Deadline: October 23, 2026.

## Objective and current checkpoint

Rove is a private, map-first Bay Area transit prototype covering BART, Muni, VTA, AC Transit, and Caltrain. Preserve the current interface and repository history. Do not deploy publicly without Sahil's explicit approval. The immediate priority is a reliable MVP, not a visual rewrite.

The geographic MapLibre interface, agency filters, route/stop search, favorites, tutorial, route highlighting, responsive panels, dark mode, static GTFS shapes, real 511 vehicle markers, arrivals, alerts, cache protection, and stale-state plumbing are implemented. Muni and AC Transit static data were repaired on October 17 using 511 static feeds and now match 511 realtime IDs exactly in the sampled live feed.

Journey planning is intentionally not implemented yet. The existing Plan control states that a routing engine is required and does not fabricate results.

## Repository and architecture

- Private GitHub repository: `https://github.com/SahilGBhuva/rove`
- Branch: `main`
- Frontend: plain HTML, CSS, and JavaScript (`index.html`, `styles.css`, `app.js`)
- Map: MapLibre GL JS with the OpenFreeMap style and visible provider/OSM attribution
- Static browser dataset: `public/data/network.json`, generated by `scripts/build-data.mjs`
- Local backend: `server.mjs`, Node HTTP server and 511 GTFS-Realtime proxy
- GTFS-Realtime decoding: `gtfs-realtime-bindings`
- Secret: `SF_511_API_KEY` in local `.env`, server-side only
- Raw/extracted GTFS: `data/raw/` and `data/extracted/`, deliberately ignored by Git

The server uses an explicit static-file allowlist. Only `index.html`, `app.js`, `styles.css`, and files under `public/` are web-accessible. Requests for `.env`, `.git`, scripts, raw data, and backend files return 404.

## Realtime implementation and verified status

`server.mjs` fetches the 511 regional (`agency=RG`) protobuf feeds server-side:

- Vehicle Positions: 120-second cache, stale after 270 seconds
- Trip Updates: 180-second cache, stale after 390 seconds
- Service Alerts: 900-second cache, stale after 1,230 seconds
- Rolling hard cap: 54 upstream requests/hour under the default 60/hour limit
- Concurrent requests are coalesced; last-good data is retained within stale windows

The browser requests `/api/realtime` once per minute while visible, pauses while hidden, and refreshes immediately when foregrounded. The API key never reaches browser code or browser network requests.

Live verification on October 17 decoded 1,463 vehicles, 2,559 trip updates, and 115 alerts. The key and all three endpoints worked; feeds were fresh.

## Security requirements

Never print, commit, log, upload, or place `SF_511_API_KEY` in a URL shown to the user. Do not read or echo `.env` contents. It is mode `600`, ignored by Git, and loaded only by Node.

Before every commit/push:

```bash
npm run check-secrets
git status --short
git diff --check
```

Also verify these local HTTP results: `.env`, `.git/config`, `server.mjs`, and `scripts/configure-511-key.sh` must return 404; `app.js` and `public/data/network.json` must return 200.

## Known limitations

- No journey routing engine is connected.
- Only Muni and AC Transit have fully verified 511 static/realtime joins at this checkpoint.
- Vehicle direction labels are limited by available feed fields and static enrichment.
- The in-memory rate counter/cache assumes one local server process. Multi-instance production deployment would need a distributed lock/cache.
- The app has not been publicly deployed and must remain private until Sahil approves launch.
- Legal/attribution review remains required before public launch, including 511, SFMTA, AC Transit, BART, OpenStreetMap, and tile-provider terms.

## Claude backend checkpoint (October 17, 2026, branch `claude-development`)

Backend only; `index.html`, `styles.css` and `app.js` are unchanged. The frontend contract is in `docs/API_CONTRACT.md`; OTP operations are in `docs/ROUTING.md`.

- `server.mjs` is now a thin bootstrap. Logic lives in `lib/` (`agencies`, `gtfs/static-index`, `realtime/{decode,feed-cache,match,match-log,service}`, `routing/otp`, `stops-search`, `app`). The static-file allowlist and 404 boundary are unchanged and covered by tests.
- Exact realtime index: every trip update and vehicle is resolved server-side by agency + trip_id + service date against static GTFS. Route ids always come from static `trips.txt` (fixes Caltrain, and VTA's 76.9% route match). Stops resolve by exact stop_id, unique stop_code (VTA), or (trip_id, stop_sequence); disagreements are conflicts and never guessed. The browser's fuzzy matcher now receives only exact `PREFIX:id` values or empty strings.
- Live quality gate: arrivals for an agency are exposed only when the current feed shows at least 99% trip and stop match, no conflicts, and at least 20 predictions. Hourly match rates go to `data/reports/match-rates.jsonl` and `/api/v2/realtime/quality`.
- BART direct GTFS-RT trip updates and alerts (key-free) replace 511's BART entries when live; 511 remains the fallback. Antioch 600-range trip ids are reported as documented exceptions. No BART vehicle positions are produced.
- Cancellations, skipped stops and NO_DATA stops carry no prediction times and are reported separately.
- Fixed a pre-existing cache bug: after a rate-limited response the in-flight slot was never cleared, so every later request returned the same rate-limited result.
- OpenTripPlanner 2.8.1: setup/build/start scripts, committed build and router configs, `/api/v2/plan` (planConnection) and `/api/v2/plan/status`, `/api/v2/stops/search`. The query and variables are validated against the 2.8.1 schema in tests.
- Tests: `npm test` (node:test, 56 tests: matching, cancellations, skipped/NO_DATA stops, stale and rate-limited feeds, missing predictions, routing normalisation and errors, HTTP boundary, real-GTFS checks).

Not yet verified live (blocked in Claude's environments by the network allowlist, and by the 511 key living only on Sahil's Mac): the OTP graph build and real itineraries (`npm run otp:setup && npm run otp:build && npm run otp:start`, then `npm run verify-routing`), and live VTA/Caltrain/BART match rates (`npm start`, then `npm run verify-realtime`).
